# zipnative-mcp v1.0.0 — First stable release

<!-- GitHub Release title: v1.0.0 — first stable release -->

_Released 2026-09-07_

**Built on:** [zipnative v1.0.0](https://github.com/Nizoka/zipnative/releases/tag/v1.0.0)

The first stable release — and the first npm publication — of the Model Context
Protocol server for zipnative, the zero-dependency TypeScript ZIP engine. 13 tools
expose the engine's frozen 1.0 surface to any MCP client: inspect and list without
extracting, random-access reads, one-call verification, secure-by-default extraction,
forward scanning of truncated streams, path sanitizing, deterministic and reproducible
creation (store / deflate, worker-parallel, streamed sources), incremental
modification without recompression, CRC-32, bounded raw-DEFLATE inflation, an offline
capability manifest, and human-in-the-loop issue drafting. The tool API is
`_meta.apiVersion = '1.0.0'` and stable under `docs/API_STABILITY.md`; the bytes the
archive-producing tools emit are part of that contract. Three runtime dependencies,
no network code path, and every archive the server writes validated against ISO/IEC
21320-1:2015 by a blocking, engine-independent conformance gate.

## Highlights

- **Full engine coverage, honestly graded** — every one of zipnative's 77 exports is mapped to a tool touchpoint or deliberately unexposed with a reason (`docs/KNOWLEDGE_BASE.md` §8; `describe_engine.unexposed` reports the same list at runtime). The 39 frozen `ZIP_*` error codes reach the client verbatim in `_meta.error.code`, with the engine's remedy in the message and machine-readable detail in `_meta.error.data`; the 11 diagnostics travel on every result.
- **Secure by default, relaxations by name** — zip-slip and device names, symlinks, duplicate paths, declared-size and ratio bombs, overlapping entries and central/local divergence are refused with frozen codes; `rejectTraversal`, `rejectSymlinks`, `onDuplicate` and `limits` are explicit inputs that skip or degrade to data, never write anything unsafe; per-call `limits` can never exceed the operator ceilings. One sandbox directory serves reads and writes; the server never overwrites and never touches anything outside it.
- **Reproducible archives with proof** — canonical layout by default (reproducible on one runtime), `compression.deterministic: true` for identical bytes on every runtime — the only case where `summary.deterministic` is `true` —, `parallel` compression that is byte-identical to the sequential writer, `includeSha256` in base64 and file mode, the separate structural `inspect_zip` determinism verdict (`deterministic` vs `canonicalLayout`), and `check` / `assert` to gate it in CI.
- **Verify before you trust** — `verify_zip` never fails for a problem with the archive: a structural refusal lands in `error { code }`, an encrypted or stream-only-codec entry is `skipped`, an entry with an unregistered method is reported failed, and only caller mistakes are `isError`. `scan_zip_forward` salvages the inventory of a truncated download or a cut stream that starts at a local header (it refuses an SFX prefix, which belongs to `inspect_zip`) and says on every result that its trust is `local-headers-only`.
- **The conformance authority gate ("veraZIP")** — ZIP had no veraPDF, so the engine built the first open clause-by-clause ISO/IEC 21320-1:2015 validator; this server vendors its core (an independent raw parser, never the engine's), asserts conformance on every archive a test produces, runs it over a 38-archive corpus with four negative canaries and hostile-but-conformant entries whose refusal is checked too, and blocks on Linux and Windows and before every publish. Conformance is not safety — the guards above exist on top of it.
- **MCP 2026-07-28 and the hosts of today** — stateless serving, `server/discover`, cache hints and projectable output schemas for 2026 clients; the automatic legacy `initialize` fallback for every revision the SDK negotiates (2024-10-07, 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25) for Claude Desktop, Cursor, Continue, Zed and ChatGPT. Token-frugal `verbosity: 'summary'` / `fields` projections, produced bytes delivered once as an embedded resource, native `zipnative://output/{+path}` resources, seven recipe prompts.
- **Proven autonomous** — `tests/autonomy.test.ts` replays one scripted agent scenario (S0 handshake through S17 clean shutdown: create, verify, inspect, list, read, inflate, CRC, modify append then compact, extract, resources, forward scan, hostile refusals, ceilings, protocol errors, a governance draft, prompts) against the built CLI on stdio legacy, stdio modern, HTTP legacy and HTTP modern with a bearer token, under a sandbox, a cache directory and lowered ceilings — no interaction, no unexpected `isError`, a code and a remedy on every refusal, JSON-only stdout. The repository's `.mcp.json` lets a human replay it from Claude Code (`docs/guides/LOCAL_TESTING.md`).
- **On npm via Trusted Publishing** — OIDC, provenance attestations (`npm audit signatures`), a CycloneDX SBOM on the Release, the full gate re-run between the Release click and `npm publish`.

## Security

- **No network, ever** — there is no network code path in the server: no telemetry, no GitHub, no URL from any argument, no egress opt-in. `describe_engine.network` is `'none'`; every tool advertises `openWorldHint: false`; `draft_governance_issue` produces a local draft and stops.
- **feat(security):** one filesystem boundary (`ZIPNATIVE_MCP_OUTPUT_DIR`) for `zipPath` / `sourcePath` / `resources/read` reads and file-mode writes — relative paths only, NUL / absolute / UNC / `..` refused, container-extension allow-list, realpath re-check after every `mkdir -p` and of every file read (a planted symlink or junction is `SECURITY_VIOLATION` on reads as on writes), `wx` opens, partial files removed; unset = no file I/O beyond the opt-in response cache.
- **feat(security):** operator ceilings `ZIPNATIVE_MCP_MAX_UNCOMPRESSED_BYTES`, `ZIPNATIVE_MCP_MAX_ENTRIES`, `ZIPNATIVE_MCP_WORKERS` bound every per-call `limits`, `scan_zip_forward.maxEntries` and `create_zip.parallel.workers` (`LIMIT_CEILING_EXCEEDED` names the variable; an invalid value refuses to start); a byte envelope on every exchange (256 MiB frame, 128 MiB decoded input, 16 / 32 / 50 MiB inline caps, 4 GiB streamed file output, 200 diagnostics); mandatory `maxOutput` on `inflate_raw`.
- **feat(security):** the engine's code-injection points (`registerCodec`, `setInflateImpl`, `setDeflateImpl`, `ParallelZipOptions.workerUrl`) are unexposed; strict Zod at every nesting level; base64 diagnosed at the boundary; loopback HTTP with Host / Origin guard and a pinned Origin port, opt-in constant-time bearer token, 405 / 413 where due.
- **No encryption by policy** — encrypted entries are detected (`ZIP_UNSUPPORTED_ENCRYPTION`), never decrypted, never silently skipped by the default extraction.
- **docs(security):** SECURITY.md states the supported-versions policy (`1.0.x`), the threat model (LLM untrusted, archives untrusted, host trusted, one sandbox), what is and is not defended, "Network egress: none", release integrity and the compatibility promise.

## Added

- **feat(tool): inspect_zip** — one-call archive report with the structural determinism verdict, every diagnostic, `check[]` (15 assertions) and `assert {…}` → `checks[]` / `checksPassed`; eager validation by default (every entry's real extent checked up front).
- **feat(tool): list_zip_entries** — paged, filterable central-directory inventory on the shared `EntryView` row (decoded flags, Unix mode, `sanitizedPath`, named extra fields, `rawNameHex`).
- **feat(tool): read_zip_entry** — one entry by `name` or `index`; `mode: 'data'` (base64 / UTF-8 text, CRC-verified, `range` window), `'raw'` (compressed payload), `'verify'` (single-entry check).
- **feat(tool): verify_zip** — the engine's report verbatim; never `isError` for an archive problem (an unregistered-method entry is reported failed, not skipped); `entries` selection and `maxEntries`.
- **feat(tool): extract_zip** — guards on by default, an eager pre-flight so the dry run refuses hostile extents before any plan, inline caps, streamed file mode under a relative `outputDir` with `resource_link`s, `emptyDirectories`, skipped-unsafe listing.

- **feat(tool): create_zip** — inline / sandbox / streamed entries (up to 100 000; Zip64 auto-promotion reachable), canonical or insertion order, pinned dates, archive and per-entry compression with the deterministic pin (the only case reporting `summary.deterministic: true`), comments, attributes, extra fields, `parallel` (engine default worker count bounded by the ceiling), `chunkSize`, `includeSha256` in base64 and file mode; a typed `summary { deterministic, deflateTier, parallel, sha256 }`.

## Upgrade

First release — nothing to upgrade from. The tool API starts at `1.0.0`; from here on, `docs/API_STABILITY.md` governs every change (produced bytes are byte-identical across patch and minor releases; a change to them is major).

## Known limitations

- **No encryption** — encrypted entries are detected and refused (`ZIP_UNSUPPORTED_ENCRYPTION`); there is no password input anywhere. ZipCrypto is broken by design; AES read-only waits on an engine provider (ROADMAP).
- **Forward reader bit-3 exclusions** — `scan_zip_forward` refuses store + data-descriptor, encrypted + data-descriptor and custom-codec + data-descriptor entries (`ZIP_UNSUPPORTED_CD_LESS_DESCRIPTOR`): they are structurally undelimitable without the central directory. Use the whole archive with the authoritative readers.
- **Streamed entries above 4 GiB** — `create_zip` `stream: true` on a source larger than 4 GiB is refused (`ZIP_UNSUPPORTED_ZIP64_STREAMING`); buffered entries are fully Zip64. Per-entry Zip64 streaming lands with the engine (ROADMAP).
- **Inline caps** — 16 MiB per entry, 32 MiB per extraction, 50 MiB per produced archive or inflated stream, 128 MiB decoded input per call. Above them: `outputMode: 'file'` (needs the sandbox), a `filter`, or a `range`.
- **No superset gate before 1.1.0** — `tests/_fixtures/tool-shape.v1.0.0.json` freezes this catalogue; the compatibility comparison against it starts with the first release that has something to compare (the parity gate against `tool-shape.json` is active now).
- **No codec beyond store / deflate** — `inflate_raw` with another method id answers `ZIP_UNSUPPORTED_METHOD`; `registerCodec` is executable code and stays unexposed.
- **Append-mode remanence** — `modify_zip mode: 'append'` keeps removed / replaced payloads inside the file (documented on the tool; `mode: 'compact'` deletes for real), and 7-Zip reads the stale payload of such an archive.

## Downstream integration notes

- **Error envelope** — every failure is `isError: true` with `content[0].text = "<tool> failed [CODE]: message"` and `_meta.error = { code, message, data? }`; `code` is one of the 16 wrapper codes or one of the 39 frozen `ZIP_*` codes verbatim (`docs/data/errors.json` is the registry, shared with the engine and the CLI). Branch on `code` and `data.errorClass`, never on the message. `verify_zip` is the exception by design: archive problems are a successful result with `ok: false` / `error { code }`.
- **Resource URIs** — files in the sandbox are `zipnative://output/<relative path>` (template `zipnative://output/{+path}`), listed by `resources/list`, read by `resources/read` (≤ 50 MiB), and linked as `resource_link` blocks from `create_zip`, `modify_zip`, `inflate_raw` and `extract_zip` in file mode (a file-mode `draft_governance_issue` result carries two text blocks; its draft is listed by `resources/list` instead). Produced bytes in base64 mode arrive as an embedded `resource` block (`data:application/zip;base64,…`; `application/octet-stream` for `inflate_raw`), never duplicated into `structuredContent`.
- **Environment variables (7)** — `ZIPNATIVE_MCP_OUTPUT_DIR` (sandbox for reads and writes; unset = base64 only), `ZIPNATIVE_MCP_CACHE_DIR`, `ZIPNATIVE_MCP_PORT`, `ZIPNATIVE_MCP_HTTP_TOKEN` (secret, ≥ 16 chars), `ZIPNATIVE_MCP_MAX_UNCOMPRESSED_BYTES` (default 8 GiB), `ZIPNATIVE_MCP_MAX_ENTRIES` (default 100 000), `ZIPNATIVE_MCP_WORKERS` (default 8, `0` disables). None carries an egress role. `server.json` lists them.
- **Shared vocabulary with the CLI** — the `EntryView` row, the `limits` keys, the `inspect_zip` report and `check` names, the `verify_zip` report, the diagnostic rows and `docs/data/errors.json` mirror `zipnative-cli`'s `--json` shapes, so an agent that knows one reads the other.
- **Engine pin** — `zipnative ^1.0.0`; the engine's `docs/assets/ecosystem.json` records this server's version and pin. An engine minor that adds a `ZIP_*` code fails `tsc` here until mapped (a wrapper minor); an engine major is a wrapper major.
- **Programmatic use** — `createServer()`, `callToolDirect()`, `listToolsPayload()`, `ensureEngineReady()` and the `ToolError` classes are exported from the package entry for embedding in another Node process.
