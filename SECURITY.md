# Security Policy

## Supported versions

The latest published minor on npm receives security patches. Older versions are unsupported once a new minor lands.

| Version | Supported |
| ------- | --------- |
| `1.1.x` | yes |
| `< 1.1` | no |

## Reporting a vulnerability

**Please do not open a public GitHub issue for security problems.**

Report suspected vulnerabilities privately via GitHub Security Advisories:
<https://github.com/Nizoka/zipnative-mcp/security/advisories/new> (**Security → Report a vulnerability** on the repository). Include:

- A description of the vulnerability.
- Reproduction steps or a minimal proof of concept — for an archive-shaped issue, the archive itself (or the `create_zip` arguments that produce it) and the tool call.
- The version of `zipnative-mcp`, `zipnative` and Node.js you tested against.
- Any suggested mitigation.

You will receive an acknowledgement within **7 days**. We aim to ship a fix and a coordinated public advisory within **30 days** of the initial report (or sooner for critical issues). Engine-level findings (parser, writer, extraction guards, the byte-range reader, canonicalisation) belong to [Nizoka/zipnative](https://github.com/Nizoka/zipnative/security/advisories/new) — report to both when unsure. The machine-readable policy is [`.github/SECURITY-INSIGHTS.yml`](.github/SECURITY-INSIGHTS.yml).

## Threat model

`zipnative-mcp` is designed to run as a local MCP server, spawned by a trusted host (Claude Desktop, Cursor, etc.) and communicating over stdio (or a loopback-only Streamable HTTP endpoint when `ZIPNATIVE_MCP_PORT` is set). The threat model assumes:

- The **host process is trusted** (the user installed it themselves).
- The **operator** who sets the environment variables is trusted.
- The **LLM controlling the host is untrusted** — it may send arbitrary, malicious tool arguments (names, paths, globs, limits, base64).
- **Archive inputs are untrusted** — every header, name, size, flag and payload may lie.
- **Other processes that can write into the sandbox are not trusted to keep a file still** — a file may be swapped, grown or truncated while a tool reads it.
- The **filesystem outside `ZIPNATIVE_MCP_OUTPUT_DIR` must remain inaccessible** — for reads as much as for writes; with the variable unset the server performs no file I/O except the opt-in response cache under `ZIPNATIVE_MCP_CACHE_DIR` (see below).

In particular we defend against (details and CWE ids in [docs/guides/SECURITY.md](docs/guides/SECURITY.md)):

- **Zip-slip path traversal and Windows reserved device names** (`../`, absolute paths, drive letters, backslashes, UNC, NUL, NTFS alternate data streams, `CON` / `NUL` / `COM1`…) — the engine's `rejectTraversal: true` default in `extract_zip`; the engine's sanitized path is the only thing ever joined onto the output directory; `sanitize_entry_paths` exposes the same gate for external sinks. Relaxing it *skips* unsafe names, never emits them.
- **Decompression bombs** (high ratio, nesting, entry floods) — the engine's nine `ZipLimits` bounds, enforced *during* inflation; per-call `limits` can never exceed the operator ceilings `ZIPNATIVE_MCP_MAX_UNCOMPRESSED_BYTES` and `ZIPNATIVE_MCP_MAX_ENTRIES`, nor `parallel.workers` `ZIPNATIVE_MCP_WORKERS` (`LIMIT_CEILING_EXCEEDED`), and the fourth ceiling, `ZIPNATIVE_MCP_MAX_FILE_OUTPUT_BYTES`, caps every file written (`OUTPUT_TOO_LARGE`); an invalid ceiling refuses to start; `inflate_raw` requires a `maxOutput` bound. The byte-range reader fetches one entry's compressed payload at most `limits.maxEntryCompressedSize` bytes (CWE-770), bounded by the uncompressed ceiling.
- **Regular-expression denial of service (CWE-1333)** — an archive controls the entry names a glob is matched against. Globs compile to a token list run as a Thompson NFA: one match is O(name × pattern) whatever the input (`*a*a*a` over a 2 000-character name took seconds through the 1.0.0 backtracking translation); a pattern is at most 1 024 characters (a literal entry name longer than that — legal up to 4 096 bytes — is selected with `names` or `prefix`); an invalid class range is `VALIDATION_ERROR`. The dependency pattern of `draft_governance_issue` no longer backtracks either, and its free-text fields are bounded at 16 384 characters. `tests/filter.test.ts` and `tests/governance.test.ts` carry timing locks.
- **Symlink entries** — `rejectSymlinks: true` by default; a symlink accepted through `rejectSymlinks: false` is written as a regular file holding the link target text, never materialised as a link. A symlink or junction pre-planted inside the sandbox cannot redirect a write outside it (realpath re-check after every `mkdir -p`) nor a read (`SECURITY_VIOLATION`; a dangling link is `INPUT_NOT_FOUND`).
- **Sandbox read races (TOCTOU, CWE-367)** — every read of a sandbox file (`zipPath`, `sourcePath` buffered and streamed, a `merge_zip` source, the forward scanner's stream, a byte-range reader, `resources/read`) goes through **one open handle**: open, `fstat`, the real path proven inside the sandbox and bound to the handle by device and inode, then only the handle is read. A path swapped while it was being opened is `SECURITY_VIOLATION`; a file that grows or shrinks under the read is `IO_ERROR` (`data.remedy: 'retry'`), never served. The opt-in response cache lives outside the sandbox: it reads an entry's age and bytes through one descriptor (nothing can be swapped between the two), with no real-path or device / inode binding — protect its directory.
- **Overlapping entries, central-vs-local header differentials, Zip64 sentinel spoofing, ambiguous EOCD records** — always-on engine checks with no opt-out (`ZIP_ENTRY_OVERLAP`, `ZIP_CD_LFH_MISMATCH`, `ZIP_ZIP64_CONTRADICTION`, `ZIP_EOCD_NOT_FOUND`). `modify_zip` opens its input with `validate: 'eager'` in both modes: the append path never re-reads the existing entries, so a lazily opened archive with overlapping entries or a truncated local header was re-emitted unchecked in 1.0.0; both are now refused before any operation runs (found by the seeded fuzz suite, locked by test F-001). Because that eager pass checks extents only, the append path also reads every non-encrypted entry raw before saving (its local header and declared sizes, nothing decompressed), so a method / CRC / size divergence (`ZIP_CD_LFH_MISMATCH`) or a declared-size bomb (`ZIP_LIMIT_EXCEEDED`) is refused as compaction and the other writers refuse it.
- **Corrupt content propagated by a rewrite** — `merge_zip` checks every entry's CRC and size before transplanting it (`verify: true` by default), refuses an entry it cannot check (a method with no codec here, `ZIP_UNSUPPORTED_METHOD`) and refuses encrypted entries; the engine's `addRaw()`, where the caller vouches for CRC and sizes, is not exposed. `canonicalize_zip` and `modify_zip` copy payloads bit for bit and decode nothing — a corrupt payload, and an unsafe name such as `../../evil.txt`, already in their input is carried into their output (`extract_zip` still refuses the name; `merge_zip` refuses it with `ZIP_INVALID_ENTRY_NAME`).
- **Duplicate entry names shadowing each other** — `onDuplicate: 'error'` by default; `merge_zip` `onConflict: 'error'` by default.
- **Sandbox escape through tool arguments** — every path (`zipPath`, `sourcePath`, a `merge_zip` source, `outputPath`, `outputDir`, a `resources/read` URI) resolves through one module: relative only, NUL / absolute / UNC / `..` rejected, container-extension allow-list on archive paths, the real path of the file read or of the parent written checked against the real sandbox. The byte-range reader is fed only by a sandbox file handle or inline bytes — there is no URL form.
- **Path disclosure and uncoded failures** — every `ZipError` keeps its frozen code; anything else that escapes the engine or the runtime is `ENGINE_ERROR` with `data.errorClass: 'internal'` and its message stripped of absolute paths (`redactAbsolutePaths`); `IO_ERROR` never carries an absolute path either.
- **Arbitrary file overwrite** — every write opens with `wx` (`OUTPUT_EXISTS`); partial files are removed on failure and on cancellation; the input archive is never touched.
- **Runaway work after the client gave up** — a cancelled request (`notifications/cancelled`, or an HTTP client that goes away) stops every tool whose work scales with its input between chunks (the engine releases stream locks and worker pools), removes a partial output file and is never cached; over MCP it gets no response, in-process it ends with `CANCELLED`. **Not covered:** `verify_zip` — zipnative's `verifyZip` is synchronous and takes no signal, so a started verification runs to completion and holds the event loop meanwhile (bounded by the input caps and `limits`; an engine limitation).
- **Resource exhaustion through the exchange** — 256 MiB stdio frame / HTTP body cap (413), 128 MiB decoded base64 input per call, 1 GiB buffered path input, 32 merge sources and 1 GiB of them in all, 16 MiB per inline entry, 32 MiB per inline extraction, 50 MiB per inline output, a file-output ceiling enforced while writing (`ZIPNATIVE_MCP_MAX_FILE_OUTPUT_BYTES`, 4 GiB by default), bounded JSON shapes, 200 diagnostics per result.
- **Prototype pollution** — `additionalProperties: false` on every JSON Schema input object; Zod strict objects at every nesting level (unknown keys are rejected with `VALIDATION_ERROR`; the one key the server never sees is a `__proto__` at the root of `arguments`, which the MCP SDK's envelope parsing removes before dispatch — nothing reaches a prototype chain either way, and an object whose prototype was replaced is refused by the input boundary); `fields` paths refuse `__proto__` / `constructor` / `prototype` segments, and the projection walks own properties only and merges with `defineProperty` (`tests/prototype-pollution.test.ts`).
- **Malformed base64 at the boundary** — `data:` URIs, PEM text, nested URIs, double-encoded or empty payloads are rejected with a coded error before the engine runs.
- **Code injection through the engine's extension points** — `registerCodec`, `setInflateImpl`, `setDeflateImpl`, `nameDecoder` and `ParallelZipOptions.workerUrl` are not exposed; no tool argument can name a module, a function or a worker script (`describe_engine.unexposed`).
- **DNS rebinding against the HTTP transport** — bound to `127.0.0.1`, foreign `Host` / `Origin` answered with 403 before the request body is read, the `Origin` port pinned to the server port, `GET` / `DELETE` with 405.
- **Slow or oversized HTTP requests** — a 30 s headers timeout, a 300 s request timeout, a 5 s keep-alive timeout and at most 100 request headers; every response carries `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`. The server refuses to start on a `ZIPNATIVE_MCP_PORT` that is not an integer in 1–65535 or a relative `ZIPNATIVE_MCP_OUTPUT_DIR` / `ZIPNATIVE_MCP_CACHE_DIR`.
- **Unauthenticated local access to the HTTP transport** — *only when the operator opts in:* `ZIPNATIVE_MCP_HTTP_TOKEN` (≥ 16 characters, no whitespace; a weaker value aborts startup) makes every request to `/mcp` require `Authorization: Bearer <token>`; anything else is answered `401` with `WWW-Authenticate: Bearer realm="zipnative-mcp"` — followed by `, error="invalid_token"` only when the request carried credentials, per RFC 6750 §3.1 — before the request body is read and before the MCP handler runs. The comparison is constant-time (SHA-256 + `timingSafeEqual`) and the token is never logged or echoed. stdio mode needs no token (the host owns the pipe).
- **Listener exhaustion on keep-alive HTTP connections** — disconnect detection is attached per response, not per socket.
- **Diagnostics corrupting the stdio wire** — a diagnostics sink is installed on every engine call that accepts one (`verifyZip` returns its diagnostics in its report instead), so the engine's `console.warn` fallback is never reached; ESLint's `no-console` and the gate's `smoke` and `dist-probe` steps keep stdout for JSON-RPC frames only.

**Hostile-input testing.** `tests/zip-fuzz.test.ts` drives mutated archives through every reader, verdict and rewriter tool, and hostile values into every top-level input of every tool; the invariant is a success or a documented code, and a rewriter's output from a mutated input must still be a valid, ISO/IEC 21320-1 conformant archive. It is **seeded** (`tests/_fuzz.ts`, mulberry32): the same cases run on every machine, so it is a deterministic regression net. **There is no coverage-guided fuzzing** in this repository; parser fuzzing belongs to the engine.

We do **not** currently defend against:

- **Other local processes reaching the HTTP endpoint when `ZIPNATIVE_MCP_HTTP_TOKEN` is unset.** The default HTTP mode (`ZIPNATIVE_MCP_PORT` without a token) has **no authentication**: the loopback bind and the Host / Origin guard stop browsers and remote hosts, not a process running on the same machine. Set the token whenever anything untrusted can run locally; the startup log states which mode is active (`bearer token required` / `no authentication (loopback only)`).
- **Encrypted archives.** There is no decryption: the engine 1.x has no AES (an engine 2.0 candidate) and ZipCrypto is broken by design, so supporting it would create false confidence. Encrypted entries are detected and refused with `ZIP_UNSUPPORTED_ENCRYPTION` — never decrypted, never silently skipped by the default extraction.
- **Content of extracted files.** The server does not execute, render or scan what it extracts; treat content from an untrusted archive as untrusted in the caller.
- **The forward reader's trust caveat.** `scan_zip_forward` reads local headers alone and says so (`trust: 'local-headers-only'`); a hostile archive can present different content there than the authoritative readers report. Use it only for streams you cannot seek and never feed its names to a filesystem without `sanitize_entry_paths`.
- **Data remanence of `modify_zip mode: 'append'`.** The append-only save keeps original bytes verbatim, so removed or replaced payloads remain recoverable from the output; `mode: 'compact'` is the true deletion path. Documented loudly on the tool.
- **`merge_zip` with `verify: false`.** The caller then trusts the sources: their compressed bytes travel as they are, corrupt or not.
- **A maliciously-crafted archive causing a crash inside `zipnative`** beyond what its own test and fuzz suites cover (the engine is responsible for parser hardening — please report such issues to both projects). Any escape is classified `ENGINE_ERROR`, never an uncoded failure.
- **Anything stored in the opt-in response cache** (`ZIPNATIVE_MCP_CACHE_DIR`) — it writes tool output as plaintext at rest, which is why path inputs, file-mode calls, wall-clock and worker calls, cancelled calls, `describe_engine` and `draft_governance_issue` are never cached; protect the directory like the output sandbox.
- **A residual window between the realpath check of the parent and the exclusive open** in file mode — the documented posture is "use an empty or trusted destination". Reads have no such window (one handle).

## Network egress: none

The server makes **no outbound network call, ever**. There is no network code path: no `fetch`, no socket other than the opt-in loopback listener that *receives* MCP requests. No tool argument, environment variable or archive content can name a URL; the engine's byte-range reader (`openZipRange`) is fed only by a sandbox file handle or inline bytes, never by a remote source; nothing is sent to GitHub or to a telemetry endpoint; `draft_governance_issue` produces a local draft and stops. `describe_engine.network` is the constant `'none'`, every tool advertises `openWorldHint: false`, and `tests/no-network.test.ts` holds the source tree to it (no `fetch(`, `https`, `dns`, `net` or WebSocket under `src/`; `node:http` only in the loopback listener).

The 8 environment variables carry no egress role: `ZIPNATIVE_MCP_OUTPUT_DIR` (the sandbox for reads and writes; unset = no file I/O beyond the cache), `ZIPNATIVE_MCP_CACHE_DIR` (opt-in response cache), `ZIPNATIVE_MCP_PORT` (loopback HTTP transport), `ZIPNATIVE_MCP_HTTP_TOKEN` (**secret**, bearer token for that transport), `ZIPNATIVE_MCP_MAX_UNCOMPRESSED_BYTES`, `ZIPNATIVE_MCP_MAX_ENTRIES`, `ZIPNATIVE_MCP_WORKERS`, `ZIPNATIVE_MCP_MAX_FILE_OUTPUT_BYTES` (operator ceilings). All eight are declared in `server.json` and validated at startup (the four ceilings are read once, at boot); an invalid value refuses to start, never a silent fallback.

## Operator knobs and vocabularies

- **8 environment variables** — the list above; the four ceilings are reported by `describe_engine.ceilings` with `env` naming each variable, and a refusal above one carries `data.env`.
- **17 wrapper codes** (`src/wrapper-codes.ts`, each with its meaning and remedy): `VALIDATION_ERROR`, `INPUT_TOO_LARGE`, `INPUT_NOT_FOUND`, `ENTRY_TOO_LARGE`, `ENTRY_NOT_UTF8`, `OUTPUT_TOO_LARGE`, `OUTPUT_EXISTS`, `IO_ERROR`, `SECURITY_VIOLATION`, `MISSING_OUTPUT_PATH`, `INVALID_PATH`, `INVALID_EXTENSION`, `LIMIT_CEILING_EXCEEDED`, `UNKNOWN_RESOURCE`, `GOVERNANCE_VIOLATION`, `CANCELLED` (new in 1.1.0), `ENGINE_ERROR`.
- **39 frozen `ZIP_*` codes** passed through verbatim, and **12 diagnostic codes** on every result (`ZIP_TIMESTAMP_CLAMPED` is new in zipnative 1.1.0 and unreachable here by design: an out-of-range date is `VALIDATION_ERROR` before the engine sees it). Registry: [docs/data/errors.json](docs/data/errors.json); the meaning and fix of every code: [docs/AGENT_CONTRACT.md](docs/AGENT_CONTRACT.md#6-error-reference).

## Reproducibility

- **UTC DOS times.** Every engine call runs with `dosTimeMode: 'utc'`: a pinned `create_zip` / `modify_zip` / `canonicalize_zip` date gives the same DOS fields on every host, and `lastModified` reads back as the same instant. 1.0.0 used the host time zone, so a pinned call made in Paris differed from the same call on a UTC runner. `tests/reproducible-build.test.ts` drives the built server under `Pacific/Kiritimati` and `America/Anchorage` and asserts identical bytes, equal to the in-process UTC call and to the 1.0.0 UTC bytes. On a non-UTC host the read side moved too: every archive's dates read back shifted by the zone offset from what 1.0.0 reported there.
- **The deterministic encoder.** `compression.deterministic: true` pins the engine's pure-TypeScript deflate encoder, so `create_zip` and `modify_zip` give the same SHA-256 on every runtime under `deterministic: true`; the default `node-zlib` tier is byte-stable per environment only. A byte change under `deterministic: true` is the engine's semver-major contract and this server's too.
- **Canonicalisation.** `canonicalize_zip` (and `modify_zip mode: 'compact'` with `canonical`) brings any archive into the engine's canonical form without recompression — no codec runs, so the result does not depend on the runtime — and reports the engine's own `analyzeDeterminism()` verdict on the output; `inspect_zip` `determinismReport` / `canonicalDate` verify it later.
- **The repository proves it on itself.** `npm run test:generate` drives every example through the built server under `TZ=UTC` with every operator variable scrubbed, and `npm run verify:samples` holds the 54 samples to `tests/_fixtures/samples.sha256.json` — byte for byte for the archives, through a semantic projection for the JSON results. The baseline is a chain: each entry records the release whose output it is (`since`), so a rebaseline shows exactly which output moved and must be declared in the release note. The check is blocking in CI (`sample-regression` is a required status check).

## Supply chain

- **Exactly three runtime dependencies** — `zipnative` (MIT, zero dependencies), `@modelcontextprotocol/server` (Apache-2.0 from 2.3.0, see [THIRD-PARTY-NOTICES.md](THIRD-PARTY-NOTICES.md)) and `zod` (MIT), and no new one, ever. `.npmrc` sets `ignore-scripts=true` and `audit-level=high`, there is no `prepare` script, and every CI install is `npm ci --ignore-scripts`, so no install-time lifecycle script runs, locally or in CI.
- **Hardened workflows** — every job starts with `step-security/harden-runner` (audit mode; the macOS leg of the gate skips it, the one documented exemption — the pinned action covers GitHub-hosted macOS runners in audit mode only), declares least-privilege `permissions` and a timeout, and checks out with `persist-credentials: false`. Every action is pinned to a full commit SHA, one SHA per action across the tree. `dependency-review` gates every dependency change on a pull request (high-severity advisories and a licence allow-list), CodeQL runs the `security-extended` queries with a config file, OpenSSF Scorecard runs on a schedule, `npm audit --audit-level=high` runs weekly on the full tree (and at `low` on the runtime tree), and `node-current` runs the gate on the current Node line.
- **One gate** — `scripts/gate.ts` is the single definition of green: `ci.yml` runs `--ci --require-all` on Linux (Node 22 and 24), Windows and macOS (`npm audit` beside it on Linux); `verazip.yml` repeats the veraZIP corpus on Linux and Windows; `sample-regression.yml` holds the sample baseline. A step that would skip fails under `--require-all`.
- **Trusted Publishing, four jobs** — `publish.yml` runs on a published GitHub Release (or a `workflow_dispatch` dry run that uploads nothing):
  1. `verify` — no `id-token`: checks the tag against `package.json` and `server.json`, installs the pinned npm 11.19.1, `npm ci --ignore-scripts`, `npm audit --audit-level=high`, runs `npx tsx scripts/gate.ts --publish --require-all`, packs **one** tarball, writes the CycloneDX SBOM with `npm sbom` (runtime dependencies, from the lockfile) and records the SHA-256 and SHA-512 integrity as job outputs.
  2. `publish` — behind the `npm-publish` environment (the maintainer configures a required reviewer on it — a repository setting, listed in the release runbook), the only job whose OIDC token can publish to npm: it checks out `.nvmrc` alone, installs only the pinned npm client (`--ignore-scripts`) and no dependency, runs no repository script, re-checks the handed-on tarball against the recorded digests and the version inside it, and runs `npm publish <tarball> --provenance --access public` — a short-lived GitHub OIDC token, no long-lived npm token.
  3. `attest` — checks that the registry serves exactly those bytes (`dist.integrity` and a byte comparison of the tarball fetched back), creates a build-provenance attestation (`actions/attest-build-provenance`) for the tarball and the SBOM, and attaches both to the GitHub Release; the only job holding `contents: write`.
  4. `registry` — publishes `server.json` to the MCP registry with `mcp-publisher` pinned by version and by the SHA-256 of its release archive, authenticated by the workflow's GitHub OIDC identity: no secret.

  Verify an install with `npm audit signatures`. `publishConfig.provenance` is set, so a publish from outside CI without an OIDC identity fails.
- **Branch and tag protection** — `.github/rulesets/main.json` and `tags.json` are the committed copies of the GitHub rulesets (required checks `ci (22)`, `ci (24)`, `os (windows-latest)`, `os (macos-latest)`, `sample-regression`, `verazip (ubuntu-latest)` and `verazip (windows-latest)`; release tags under `refs/tags/v*` are never deleted or moved); the maintainer imports them. `CODEOWNERS` and `.github/SECURITY-INSIGHTS.yml` are committed.
- **Vendored, never imported** — the veraZIP validator core, the raw ZIP builder and the interop probes are copied from the engine with their upstream commit and blob hashes pinned by `tests/verazip-vendor.test.ts`; the validator never imports `zipnative`. The interop fixtures are pinned by `tests/fixtures/SHA256SUMS` ([`tests/fixtures/PROVENANCE.md`](tests/fixtures/PROVENANCE.md)).
- **Agents never publish** — the human-in-the-loop policy (`.github/AGENT_RULES.md`, `.github/ai-governance.json`) is enforced in Claude Code sessions by `.claude/hooks/guard.mjs`, which refuses publishing, pushing, tagging and every GitHub write; the server itself has no code path that can write to GitHub.

## Compatibility promise

- The **tool API** (15 tool names, input / output schemas, the 17 wrapper codes, the `_meta.error` envelope, the 8 environment variables) is stable under [docs/API_STABILITY.md](docs/API_STABILITY.md): removals, renames and narrowings are semver-major. `tests/catalogue-superset.test.ts` holds the live `tools/list` to a superset of the frozen 1.0.0 catalogue.
- The **39 `ZIP_*` error codes** and **12 diagnostic codes** are passed through verbatim from the engine, where they are frozen; removing or renaming one is a zipnative major and therefore a zipnative-mcp major. Registry: [docs/data/errors.json](docs/data/errors.json).
- The **bytes** `create_zip`, `modify_zip`, `canonicalize_zip`, `merge_zip` and `inflate_raw` produce for a given input are byte-identical across patch and minor releases; a change to them — including the engine's `deterministic: true` encoder — is semver-major. The one deliberate 1.1.0 output change is the UTC reading of dates, which leaves every output of a UTC host unchanged (on another zone a pinned `Z` / offset date — under `deterministic: true` too — writes different DOS fields than 1.0.0 did there, and every archive's dates read back shifted by the zone offset).
- **Security defaults are never weakened** in a non-major release: `rejectTraversal`, `rejectSymlinks`, `onDuplicate: 'error'`, `merge_zip` `verify: true` and `onConflict: 'error'`, the `ZipLimits` defaults, the operator ceiling defaults, the sandbox rules and the no-overwrite rule.
